현재 변경을 검증한다. 범위: $ARGUMENTS — `backend` / `frontend` / `all`(비어 있으면 `all`)

```
이 작업 안에서 직접 실행하고 출력을 읽은 것만 통과다.
```

이전 세션 · 아까 · 에이전트의 보고는 증거가 아니다. 그 뒤에 코드가 바뀌었으면 다시 돌린다.

## 입력

- 범위 (`$ARGUMENTS`)
- 있으면: 계획한 파일 목록 (범위 밖 변경 대조용), 기대하는 API 경로 목록

## 절차

1. **verifier** 호출 (범위와, 있으면 계획한 파일 목록 · 기대 경로를 함께 넘긴다) → 검증 명령 실행, 실패 시 최초 원인 분석, 규칙 점검(심각도 포함), `all`이면 프론트 ↔ 백엔드 계약 대조, 마지막에 검증 마커 기록.
2. verifier 결과를 그대로 요약해 보고한다. **통과하지 못한 것을 통과했다고 말하지 않는다.** 미실행 검증은 이유와 함께 적는다.
3. 실패나 규칙 위반이 있으면:
   - 이 스킬만 단독으로 불렸으면 → 고치지 말고 원인과 수정 방향만 보고한다. 고칠지는 사용자가 정한다.
   - 다른 스킬의 검증 단계에서 불렸으면 → 그 스킬로 돌아가 **최초 원인만** 고친 뒤 다시 `/verify`. 같은 실패가 두 번 반복되면 멈추고 보고한다 — 가설 · 시도 · 결과를 정리해 사용자와 논의한다.
4. `zz_docs/TODO.md`의 "마지막 검증" 표를 갱신한다 (범위 · 명령 · 결과 · 미실행). 이건 다음 세션이 이어받기 위한 기록이다.

## 돌려줄 형식

verifier의 형식을 그대로 쓴다: 결과(통과 / 실패 / 일부 미실행), 명령별 결과 표, 최초 실패와 원인, 규칙 위반(심각도 · 파일:줄), 계약 불일치, 범위 밖 변경 파일, 미실행 검증.

## 하지 않는 것

- 코드 수정 (단독 호출일 때). 기록 갱신은 `zz_docs/TODO.md`만
- 실패 로그 전체 붙여넣기 — 최초 실패 구간만
- 마이그레이션 · commit · push · 설치 명령 실행
- `node_modules`가 없을 때 임의로 `npm install` — 필요하다고 보고만
