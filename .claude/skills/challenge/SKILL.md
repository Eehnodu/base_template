$ARGUMENTS 의 주장 · 설계를 근거로 검토한다. **동의하려고 시작하지 않는다.** 장점도 반론도 base 코드 · 설정 · 문서에서 확인한 것만 근거로 쓰고, 근거가 없으면 "확인 못 함"으로 둔다.

## 입력

- 필수: 검토할 주장 · 설계 (인자 또는 직전 대화의 제안)
- 모드 (비우면 `full`):

| 모드 | 언제 | 하는 것 |
| ---- | ---- | ------- |
| `full` | 설계 · 계획을 처음 검토할 때 | 아래 4단계 전부 |
| `steelman` | 방어할 입장을 준비할 때 | 1 · 2단계만 — 가장 강한 옹호와 가장 강한 반론. 다음 단계 없음 |
| `decision` | 분석은 끝났고 결정만 남았을 때 | 4단계만 — 트레이드오프 표 + 결정 |

## 4단계

1. **근거 있는 장점.** 잘 받쳐진 점, 남다른 시각. 왜 사소하지 않은지 말한다. 일반적 칭찬("좋은 접근입니다")은 쓰지 않는다.
2. **반론.** 가정 · 편향을 묻고, 논리 공백 · 과도한 일반화 · 반례를 찾는다. base 안의 유사 코드 · 과거 결정(`zz_docs/`, CHANGELOG) · 규칙(`rules/`)과 대조한다. 반례는 파일:줄로.
3. **대안.** 다른 틀 · 방법 · 참고. 모르는 조건은 추측하지 않고 묻는다.
4. **종합.** 양쪽의 강한 요소를 합쳐 다음 단계로. 남은 불확실성과 확신도(예: "70% — 운영 데이터 없음")를 적는다. `decision` 이면 표로:

```
| 선택지 | 얻는 것 | 잃는 것 | 되돌리기 비용 |
| ------ | ------- | ------- | ------------- |
결정: [하나] — 이유 한 줄. 틀렸을 때 신호: [무엇을 보면 되돌릴지]
```

## 규칙

- 아첨도 비관도 없다. 의미 없는 문장("주목할 점은", "흥미롭게도")과 의견만 있는 문장을 쓰지 않는다.
- 사용자가 선호와 사실을 섞어 말하면 갈라서 다룬다.
- 외부 사실(라이브러리 동작 · 수치)은 출처(문서 URL · 버전)를 붙인다. 없으면 "확인 필요".
- 모르면 모른다고 하고, 무엇으로 확인할 수 있는지(명령 · 실험 · 질문)를 적는다.
- 문체는 `rules/writing.md`. 결론을 먼저 쓴다.

## 하지 않는 것

- 파일 수정. Bash는 `git log` · `git diff`처럼 읽는 용도만
- 근거 없는 반론을 반론처럼 쓰기, 근거 없는 동의
- 사용자가 이미 내린 결정을 다시 여는 것 — 새 근거가 있을 때만
