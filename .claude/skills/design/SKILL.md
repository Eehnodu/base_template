$ARGUMENTS 화면을 프론트에 구현한다. CLAUDE.md의 "작업 흐름"과 "완료 기준"을 따른다.

## 입력

- 필수: 화면 설명 (`$ARGUMENTS`)
- 있으면 좋은 것: admin · client 구분, 대상 사용자와 핵심 작업, 비범위, 제약(기존 컴포넌트 사용 · 새 라이브러리 금지 등), 확인할 화면 폭

## 1. 요청 정리

요청을 **목표 · 배경 · 범위 · 비범위 · 제약 · 수용 기준**으로 정리한다. admin 화면인지 client 화면인지, 사용자가 이 화면에서 끝내야 하는 핵심 작업, 필요한 상태(로딩 · 데이터 · 빈 목록 · 에러)를 확인한다. 모호하면 질문한다. "예쁘게" 같은 취향 표현은 사용성 기준(어떤 작업이 더 쉬워져야 하는지)으로 바꿔 확인한다.

## 2. 조사

**fe-researcher** 호출 → 관련 화면, 재사용할 공통 컴포넌트, 따를 패턴, 라우트 · 메뉴 등록 위치 조사.

## 3. 계획

아래를 정리해 보여 준다. 파일은 아직 고치지 않는다.

- `rules/frontend/design.md` 1절의 **한 줄** (admin / client, 사용자, 핵심 작업, 밀도) + 화면에 들어갈 정보를 중요도 순으로
- 배치 와이어프레임 (ASCII, 360px에서 접히는 모양 포함)
- 만들 · 고칠 파일, 추가할 라우트 · 메뉴 (에이전트에게 넘길 **담당 파일**)
- 사용할 공통 컴포넌트 · 토큰 (새로 만들어야 하는 것이 있으면 이유 — 새 토큰 · 새 공통 컴포넌트는 승인 대상)
- 화면 상태 (로딩 · 데이터 · 빈 목록 · 에러)와 반응형 · 접근성 확인 항목
- **검증이 안 다루는 실패 모드 상위 3개** (긴 텍스트, 느린 응답, 권한 없는 접근, 연속 클릭 등)와 확인 방법
- API 연동이 필요한 자리

**새 의존성, 공통 컴포넌트(`ui/`) 자체 수정, 파일 삭제 · 이동, 모호한 요구사항**이 있으면 여기서 멈추고 승인을 받는다. 없으면 계획을 알리고 진행한다. 계획이 크면(파일 5개 초과 · 단계 3개 이상) 첫 단계만 승인받고 단계마다 보고한다.

## 4. 실행

**fe-ui-builder** 호출 → 컴포넌트 · 컨테이너 작성, 라우트 · 메뉴 등록. 담당 파일 · 변경 금지 파일 · 수용 기준 · 상태 목록을 함께 넘긴다.

## 5. 검증

**`/verify frontend`** — 타입 · lint · (필요하면) 빌드 · 규칙 점검(고정색, 상태 처리 누락 등). 실패하면 최초 원인만 고치고 다시 `/verify`. 같은 실패가 두 번 반복되면 멈추고 보고한다.

기능을 마무리하는 단계면 **`/audit`**(마무리 기준)으로 화면 단위 감사도 거친다. High만 여기서 고치고 다시 `/verify frontend`.

브라우저로 직접 확인할 도구가 없으면 **못 봤다고 보고**하고, `/audit`의 브라우저 확인 목록과 합쳐 사용자가 확인할 화면 · 폭 · 조작 순서를 적는다.

## 6. 기록 · 보고

- CLAUDE.md의 "작업 기록" 규칙대로 `zz_docs/`를 갱신한다.
- 완료 기준대로 보고한다: 변경 파일과 이유, 추가한 라우트 · 메뉴, 검증 결과(못 돌린 것 · 브라우저 미확인 포함), 수용 기준 충족 여부, 묻지 않고 내린 결정, API 연동이 필요한 자리(있으면 `/fullstack` 또는 fe-api-connector로 이어서), 범위 밖 변경, 남은 위험.

## 하지 않는 것

- 조사 · 계획 단계에서 파일 수정
- 공통 컴포넌트가 있는데 같은 역할을 새로 만들기
- 고정색(hex · 기본 팔레트) 사용, 색만으로 상태 전달
- 네 가지 상태 중 일부 생략
- 요청 범위 밖 리팩터링 · 포맷 · 파일명 변경
