$ARGUMENTS 를 기준으로 색 토큰을 만들거나 고친다. 토큰은 `frontend/src/index.css`(`:root` 라이트 · `.dark` 다크, rgb 삼중값)와 `frontend/tailwind.config.js`에 있다. **색은 여기서만 정하고, 화면은 토큰만 쓴다** (`rules/frontend/conventions.md` · `design.md`).

## 입력

- 브랜드 색(hex 하나면 충분), 또는 바꿀 토큰과 이유, 또는 "검사만"
- 있으면 좋은 것: 어떤 느낌(차갑게 · 따뜻하게 · 중립), 접근성 목표(기본 WCAG AA)

## 1. 현재 상태 확인

`frontend/`에서 `python scripts/check_contrast.py --all` 을 돌려 현재 토큰의 대비 표를 받는다. 실패 · 경고가 이미 있으면 먼저 보고한다. "검사만"이면 여기서 끝.

## 2. 설계 (파일은 아직 고치지 않는다)

색 작업은 **OKLCH로 생각하고 rgb로 내보낸다.** HSL은 같은 명도값이라도 색상마다 밝기가 달라 스케일이 어긋난다.

- **primary**: 브랜드 색을 OKLCH로 표현한다. 채도는 절대값이 아니라 그 색상이 sRGB에서 낼 수 있는 최대치에 대한 비율로 생각한다 — 같은 채도 숫자여도 파랑은 선명하고 노랑은 탁해진다. 가장 선명한 명도(cusp)는 색상마다 다르다(노랑 ~0.89, 빨강 ~0.63, 파랑 ~0.46) — primary의 기본 단계를 그 근처에 두고 `-light` · `-dark`는 명도만 움직인다.
- **다크모드 값**: 라이트 값을 반전하지 않는다. 다크 배경 위에서는 **채도를 낮추고 명도를 올린** 변형을 따로 정한다. 배경은 순검정 대신 어두운 회색(현재 zinc-950/900)을 유지한다.
- **중립(zinc)**: 바꿀 이유가 없으면 그대로. 바꾼다면 브랜드 색상 쪽으로 살짝 기울인 중립(채도 ~10%, 색상 ±18° 안)을 검토한다 — 파란 회색과 붉은 회색은 다른 재료다.
- **상태색**: error 0~30° · 320~360°, warning 30~100°, success 100~200°, info 200~300° 범위 안에서 primary와 30° 이상 떨어지게. 상태 토큰(`success` · `error` · `warning` · `info`, `point-*`)은 **상태 알림에만 예약** — 장식 · 강조로 재사용하지 않는다.
- **hover · active**: 새 hex를 고르지 말고 명도만 한 단계 이동한다. 라이트(명도 > 0.5)는 어둡게, 다크(명도 ≤ 0.5)는 밝게 — 방향이 반대다.
- **색맹**: 상태색 쌍이 빨강 ↔ 초록에만 의존하면 남성 약 8%가 구분하지 못한다. 상태는 항상 아이콘 · 문구를 병행하고(`conventions.md` 화면 품질), 색 자체도 파랑 · 주황 계열이 섞이게 고른다.

설계 결과는 표로 보여 준다: 토큰 · 라이트 rgb · 다크 rgb · 바꾼 이유. **토큰 추가 · 변경은 승인 대상**이다 (CLAUDE.md 작업 흐름 — 공개 API급 변경으로 본다).

## 3. 반영

1. `index.css` — `:root`와 `.dark` **둘 다** 고친다. 주석에 참고한 Tailwind 단계나 OKLCH 값을 남긴다.
2. 새 토큰이면 `tailwind.config.js` `theme.extend.colors`에 같은 이름으로 추가하고, `conventions.md` "색상 토큰" 표에 한 줄 넣는다.
3. 새 토큰이 텍스트 · 배경으로 쓰이면 `scripts/check_contrast.py`의 `PAIRS`에 쌍을 추가한다.

## 4. 검증

- `python scripts/check_contrast.py` — 텍스트 쌍 4.5:1(본문) · UI 쌍 3:1. **라이트 · 다크 둘 다** 통과해야 한다. 실패하면 색상 · 채도는 두고 **명도만** 조정한다.
- 다크모드는 WCAG 2 공식이 가장 부정확한 영역이다(밝은 글자 on 어두운 배경은 같은 수치에서 더 낮게 보인다). 통과했어도 다크에서 브라우저 확인을 요청한다.
- `/verify frontend` (토큰 이름을 바꿨으면 빌드까지).
- 브라우저 확인 목록: 라이트 · 다크 각각 admin 로그인 · 표 화면 · 폼 에러 상태 · Toast 4종.

## 5. 보고

- 바뀐 토큰 표(전 → 후, 라이트 · 다크), 대비 검사 결과(실패 0이어야 함, 경고는 목록), 묻지 않고 내린 결정, 브라우저 확인 목록, `conventions.md` · `check_contrast.py` 갱신 여부.

## 하지 않는 것

- 화면 파일에서 색 직접 바꾸기 (토큰만)
- 라이트 값만 바꾸고 다크 방치, 또는 다크를 반전으로 만들기
- 대비 실패를 "거의 통과"로 넘기기 — 4.5 미만이면 실패
- 상태색을 장식 · 강조에 쓰기
- 검사 없이 "잘 보인다" 보고
