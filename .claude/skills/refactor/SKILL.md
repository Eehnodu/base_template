$ARGUMENTS 를 동작 유지 조건으로 리팩터링한다. CLAUDE.md의 "작업 흐름"과 "완료 기준"을 따른다. **리팩터링의 실패는 코드가 덜 예쁜 것이 아니라, 동작이 바뀌었는데 검증하지 못한 것이다.**

## 입력

- 필수: 대상 (`$ARGUMENTS`)
- 있으면 좋은 것: 목적(중복 제거 · 함수 분리 · 테스트 가능성 · 타입 정리), 유지해야 할 인터페이스, 금지 사항

## 1. 필요성 검토

파일을 고치지 않고 대상을 읽어 정리한다.

- 중복, 너무 긴 함수, 책임이 섞인 부분, 검증하기 어려운 구조
- **바꾸면 위험한 부분** (인증 · 권한 · 응답 형식 · 에러 코드 · 공통 컴포넌트 props)
- 현재 동작을 고정할 방법 (아래 3단계)

리팩터링이 필요 없거나 위험이 이득보다 크면 그렇게 보고하고 끝낸다.

## 2. 조사

대상이 백엔드면 **be-researcher**, 프론트면 **fe-researcher** 호출 → 대상을 부르는 곳(호출자 · import) 전부, 관련 타입, 기존 패턴.

## 3. 계획 (승인 필요)

아래를 보여 주고 **승인을 받는다**. 리팩터링은 항상 승인 대상이다.

- 목표와 단계 (한 단계 = 한 종류의 변경: 내부 분리 → 중복 제거 → 타입 정리 → 이름 변경 순. 한 번에 섞지 않는다)
- 단계별 담당 파일
- **유지 목록**: 함수 시그니처, API 경로 · 응답 형식 · 에러 코드, 컴포넌트 props, 화면 결과
- **금지 목록**: 공개 API 이름 변경, 오류 메시지 변경, DB 스키마 변경, 새 의존성, 전체 포맷 변경, 관련 없는 파일 수정
- **동작 유지 검증 방법**: 기존 검사(`/verify`) + 변경 전후 비교 방법. 테스트 러너가 없으므로 변경 전 응답 · 화면 결과를 기록해 두고 후에 대조한다. 대조할 방법이 없는 부분은 명시한다.

계획이 크면 첫 단계만 승인받고 단계마다 보고한다.

## 4. 실행

단계마다:

1. 백엔드면 **be-api-builder**, 프론트면 **fe-ui-builder**(연동 코드면 **fe-api-connector**)에 담당 파일 · 유지 목록 · 금지 목록을 넘겨 실행한다.
2. **`/verify`** (해당 범위)
3. `git diff --stat`으로 담당 파일 밖이 바뀌지 않았는지 확인한다.

## 5. 마무리 검증

- **`/review`** — 회귀 중심으로. code-reviewer에게 "동작 변경 여부"를 최우선으로 보게 한다.
- 3단계에서 정한 변경 전후 비교를 수행한다.

## 6. 기록 · 보고

- CLAUDE.md의 "작업 기록" 규칙대로 `zz_docs/`를 갱신한다.
- 보고: 단계별 변경 파일, **동작 변경 없음을 확인한 방법**(대조하지 못한 부분 포함), 검증 · 리뷰 결과, 묻지 않고 내린 결정, 남은 구조 문제(범위 밖).

## 하지 않는 것

- 리팩터링에 기능 변경 · 버그 수정 섞기
- 승인 없이 시작
- 여러 종류의 변경(구조 + 이름 + 타입)을 한 단계에
- 유지 목록에 있는 것 변경
- 대조하지 못했는데 "동작 동일"이라고 보고
