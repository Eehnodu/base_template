$ARGUMENTS 기능을 백엔드에 구현한다. CLAUDE.md의 "작업 흐름"과 "완료 기준"을 따른다.

## 입력

- 필수: 기능 설명 (`$ARGUMENTS`)
- 있으면 좋은 것: 배경(왜 필요한지), 비범위, 제약(기존 API 유지 · 새 의존성 금지 등), 수용 기준, 실패 처리 방식

## 1. 요청 정리

요청을 **목표 · 배경 · 범위 · 비범위 · 제약 · 수용 기준(Given / When / Then)**으로 정리한다. 빠졌거나 모호한 항목이 있으면 추측하지 말고 질문한다. 실패 상황(권한 없음 · 중복 · 대상 없음)의 처리도 여기서 정한다 — 없으면 `rules/backend/module.md` "에러 처리"의 기본대로 한다.

## 2. 조사

**be-researcher** 호출 → 관련 코드, 따를 패턴, 등록 위치, FK 대상 조사.

## 3. 계획

아래를 정리해 보여 준다. 파일은 아직 고치지 않는다.

- 만들 · 고칠 파일 목록 (에이전트에게 넘길 **담당 파일**)
- API 목록 (메서드, 경로, 로그인 필요 여부, 요청 · 응답 필드, 에러 코드)
- 모델 변경 여부와 마이그레이션 필요 여부
- **검증이 안 다루는 실패 모드 상위 3개** (권한 없는 사용자, 대상 없음, 중복, 빈 입력, 동시 요청 등)와 각각 어느 단계에서 어떻게 확인할지
- 위험 요소, 사용자에게 할 질문

**DB 모델 변경, 인증 · 권한 변경, 새 의존성, 공개 API 변경, 모호한 요구사항**이 있으면 여기서 멈추고 승인을 받는다. 없으면 계획을 알리고 진행한다. 계획이 크면(파일 5개 초과 · 단계 3개 이상) 첫 단계만 승인받고 단계마다 보고한다.

## 4. 실행

1. **be-db-modeler** 호출 → 모델 작성 (모델 변경이 없으면 건너뛴다)
2. **be-api-builder** 호출 → repository · service · router 작성, 등록

에이전트에게는 담당 파일 · 변경 금지 파일 · 수용 기준 · API 계약을 함께 넘긴다.

## 5. 검증

**`/verify backend`** — compileall · import · 라우트 등록 확인 · 규칙 점검. 실패하면 최초 원인만 고치고 다시 `/verify`. 같은 실패가 두 번 반복되면 멈추고 보고한다.

인증 · 권한 · 입력 처리를 새로 만들었으면 **`/review`**도 거친다.

## 6. 기록 · 보고

- CLAUDE.md의 "작업 기록" 규칙대로 `zz_docs/`를 갱신한다. LOGIC.md(모듈 · API · 에러 코드)도 반영한다.
- 완료 기준대로 보고한다: 변경 파일과 이유, 동작 변경, API 목록, 검증 결과(못 돌린 것 포함), 수용 기준 충족 여부, 묻지 않고 내린 결정, 범위 밖 변경, 남은 위험.
- 마이그레이션이 필요하면 `./migrate.sh "메시지"` 실행이 필요하다고 알린다.

## 하지 않는 것

- 조사 · 계획 단계에서 파일 수정
- 마이그레이션 실행, `alembic/versions/` 직접 편집
- 요청 범위 밖 리팩터링 · 포맷 · 파일명 변경
- 요청 본문의 `user_id` · `role`을 믿는 코드, `HTTPException` 직접 raise
- 검증을 못 돌렸는데 통과한 것처럼 보고
