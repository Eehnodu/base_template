$ARGUMENTS 로 30~60초 제품 소개 영상을 만든다. 렌더 엔진은 따로 설치하지 않는다. 영상용 HTML 을 시간 함수로 그리고, 헤드리스 브라우저로 프레임마다 찍어 ffmpeg 로 묶는다.

```
영상 속 사실(이름 · 숫자 · 기능 · 후기)은 프로젝트에 있는 것만. 연출 문구는 지어내도 된다.
비밀 · 실제 사용자 정보는 영상 · 문구 · 중간 파일 어디에도 들어가지 않는다.
검수는 만든 쪽이 아니라 깨끗한 컨텍스트의 서브에이전트가 프레임 번호를 근거로 한다.
```

원본: [Vincentwei1021/video-shotcraft](https://github.com/Vincentwei1021/video-shotcraft) (Apache-2.0)의 제작 절차 · 미감 규칙 · 최종 검수 · 샷 카드. Remotion 대신 HTML 프레임 렌더로, 번들 음원 대신 로컬 합성으로 바꿔 다시 썼다 (변경함).

## 입력

| 옵션 | 기본값 |
| ---- | ------ |
| 입력 | 비우면 현재 프로젝트. `http(s)://` 주소 · 도메인이면 웹사이트 |
| `--duration` | 45초 (30~60) |
| `--format` | landscape 1920x1080 (vertical 1080x1920, square 1080x1080), 30fps |
| `--features` | 비우면 조사로 고른다 |
| `--music <파일>` · `--no-music` | 로컬 합성 음악 |
| `같이 정하기` | 없으면 끝까지 스스로 정하고 진행 |

사용자가 이미 말한 용도 · 대상 · 기능 · 길이 · 비율 · 소리 조건은 바꾸지 않는다.

**진행 방식.** 기본은 0~3단계 판단을 스스로 내리고 `plan.md`에 근거와 함께 적은 뒤 끝까지 간다. "같이 정하기"면 3단계(장면표)까지 만들고 스타일프레임 · 장면표를 보여 준 뒤 멈춘다. 확인을 받으면 4단계부터 이어서 하고, 0~3단계는 다시 묻지 않는다.

## 0. 이해 · 제약 (통과 조건: 브리프 · 결정표 · 데이터 규칙이 `plan.md`에 있음)

읽기만 한다. 제품의 정체 · 주요 기능 · 화면 상태 · 색 토큰과 글꼴 · 실행 방법 · 데이터 위험을 본다.

- **브리프**: 한 문장 정의, 대상, 핵심 장점 2~3개, 꼭 보일 기능 목록(우선순위), 길이 · 비율 · 언어.
- **결정표**: `요구 | 영상에서 어떻게 할지 | 근거 파일` — 예: "대상이 휴대폰 사용자 | 세로판 + 터치 흉내 | `responsive.md`".
- **데이터 규칙**: 화면에 나올 데이터를 실제 공개 데이터 / 가짜 값 / 가림 중 하나로 정한다. 사용자 · 기록 · 랭킹 · 이메일 · 내부 주소 · 키는 가짜 값이나 가림. 공개 데이터라도 공개라는 근거가 있을 때만 그대로 둔다.

**읽지 않는 것**: `.env` · `.env.*` (CLAUDE.md 원칙 7. base 계열은 `.env`를 git 에 추적하므로 "추적 중이니 읽어도 된다"가 아니다), 키 · 인증서 · `secrets/` · `credentials/`, `dist/` · `build/` · `node_modules/`, lock 파일, `.git/`.

## 1. 시각 방향 · 스타일프레임 (통과 조건: 정지 화면 2~3장을 직접 봄)

영상 코드를 쓰기 전에 가장 싼 결과물로 색 · 글꼴 · 빛 · 움직임 성격을 정한다.

1. 방향을 최대 3개 글로 쓰고 하나를 고른다. 고른 이유와 버린 이유를 `plan.md`에.
2. `craft.md` "움직임 성격" 표에서 제품에 가장 가까운 행을 고르고 두 축(에너지 · 진지함)으로 조정해 토큰(기본 길이 · 이징 · 튕김)을 적는다. 이 토큰 하나로 등장 · 전환 · 정지를 모두 다룬다.
3. HTML/CSS 로 1920x1080 정지 화면 2~3장(`work/styleframe.html`)을 만들어 찍고 Read 로 본다. 영상은 아직 렌더하지 않는다.
4. 사용자가 참고 영상을 주면 프레임을 뽑아(`select` · `tile=4x5`) 기법을 `기법 | 참고 영상에서 | 쓸지 · 이유` 표로 정리한다. 장면마다 맞는지 따로 판단하고 영상 전체에 덮어씌우지 않는다.

## 2. 기능 → 장면 배정 (통과 조건: 꼭 보일 기능마다 장면이 하나 이상)

1. 기능 목록을 하나씩 장면에 짝짓는다. 빠진 핵심 기능은 다시 만들어야 하는 결함이다.
2. `techniques.md`에서 기능마다 1순위 · 예비 기법을 고르고 이유를 적는다. 고른 기법의 "함정"은 그대로 지킨다.
3. **한 기법은 영상 전체에서 한 번만 주인공.** 날아 들어오기 · 쌓기 · 넘기기가 두 번 나오면 하나를 바꾼다.
4. 맞는 기법이 없으면 새로 만들 수 있지만, `plan.md`에 무엇을 새로 만들었고 어떤 위험이 있는지 적는다.

## 3. 장면표 · 프레임 시간표 (통과 조건: 합계가 목표 길이와 같고, 멈춤 예산 · 확인 프레임 번호가 적힘)

전체 흐름 기본값 (프로젝트에 맞게 바꿀 수 있지만 바꾸면 이유를 적는다):

| 구간 | 비율 | 에너지 | 할 일 |
| ---- | ---- | ------ | ----- |
| 1 브랜드 오프닝 | 8~12% | 낮음 | 로고 · 이름이 자리 잡고 1초 이상 정지, 제품 화면으로 넘긴다 |
| 2 주인공 하나 | 12~15% | 중간 (가장 정성 들이고 가장 느림) | 요소 하나, 3초 이상 이어지는 동작으로 제품의 기본 단위를 보여 준다 |
| 3 기능 구간 | 55~65% | 높음과 낮음 번갈아 | 장면마다 기능 하나. 기능 장면 1~2개마다 숨 고르는 글자 카드(약 1.8초, 영상 전체 2~4장) |
| 4 마무리 | 13~16% | 가장 높음 | 지금까지 나온 기능의 대표 요소가 사방에서 모여 로고를 둘러싼다. 끝에서 1초 이상 정지 |

1. 예산을 먼저 나눈다. 1 · 2 · 4 구간과 글자 카드를 빼고 남은 프레임을 3구간에 나눈다. 각 장면 안에서 **정지 시간을 먼저 빼고** 남은 시간에 움직임을 넣는다.
2. 3구간은 높은 에너지 장면과 차분한 장면을 번갈아 둔다. 정보가 가장 많은 장면(문서 · 보고서류)은 마무리 바로 앞 2~3번째에.
3. 장면 사이 전환을 하나씩 고르고(`techniques.md` 전환), 전환 프레임은 이웃 장면 예산에서 뺀다.
4. `plan.md` 장면표: `# | 시작 프레임 | 길이 | 기능 | 화면 상태 | 기법 | 주 동작 | 소재 출처 | 자막 | 전환 | 효과음 | 확인 프레임 2개`.
5. 시간표는 한 곳(`work/timeline.js`의 `SHOTS`)에만 쓰고, 자막 · 효과음 · 전환 시점은 모두 거기서 계산한다.

## 4. 실제 화면 캡처 (통과 조건: 장면표가 요구하는 화면이 전부 있고 가짜 데이터가 들어감)

장면표가 정해진 뒤에 찍는다. 그 전에 찍은 것은 방향 확인용이고 최종 소재로 쓰지 않는다.

1. 개발 서버가 필요하다. 켜져 있지 않으면 사용자에게 켜 달라고 한다. 데이터는 0단계 규칙대로 가짜 값을 먼저 넣은 상태여야 한다 (빈 목록 · lorem ipsum 화면은 못 쓰고, 실제 사용자 데이터는 내보낼 수 없다). 가짜 값을 DB 에 넣어야 하면 방법을 사용자에게 묻는다.
2. `work/capture.mjs`로 세 가지를 만든다.
   - 페이지 전체 2배 캡처: viewport 1920x1080, `deviceScaleFactor: 2`, `fullPage`. 찍기 전 `document.fonts.ready` 뒤 600ms, 실시간 데이터가 있으면 1.5~2초 더 기다린다.
   - 요소별 컷아웃: 의미 있는 선택자로 하나씩. 떠오르는 요소는 `omitBackground`로 투명 배경. "빈 판에 카드가 날아와 앉는" 장면이 있으면 해당 요소를 `visibility:hidden`으로 숨긴 빈 판도 찍는다.
   - `layout.json`: 요소마다 페이지 좌표 `{x, y, w, h}`와 페이지 높이. 날아갈 목적지 · 가림 위치를 여기서 잡는다.
3. 페이지 · 요소 단위로 다시 찍을 수 있게 스크립트를 남긴다.
4. 이미 있는 화면은 실제 캡처를 쓴다. 손으로 다시 그리는 건 화면에 없는 요소(추상 오프닝 · 브랜드 구간)만, 그것도 실제 제품 수준의 품질일 때만.

## 5. 장면별 구현 (통과 조건: 장면마다 확인 프레임 2개를 직접 봄)

- **엔진.** `work/composition.html` 한 장에 `window.renderAt(frame)`을 둔다. 모든 상태는 프레임 번호만의 함수다. `Date.now()` · `Math.random()` · 인자 없는 `new Date()` 금지, 난수는 장면 번호에서 시드를 뽑은 고정 난수(mulberry32 등). CSS 애니메이션 · `setTimeout`에 기대지 않는다.
- **캡처.** 프로젝트의 Playwright 를 `channel: "chrome"`으로 쓴다 (없으면 설치하지 않고 사용자에게 말한다. 새 의존성은 승인 대상). 프레임마다 `renderAt(n)` → 이미지 디코드 · 글꼴 대기 → 찍기 → `work/frames/%05d.jpg`. 60초면 1,800장이라 몇 분 걸린다.
- **확인.** 장면이 끝날 때마다 장면표의 확인 프레임 2개를 `work/qa/`에 찍어 Read 로 본다. 구도 · 잘림 · 겹침 · 글자 선명도 · 떨림을 보고, 필요하면 잘라서 확대하거나 두 프레임 차이를 본다.
- **수정할 때마다 전체 렌더.** 고친 장면의 확인 프레임을 다시 보고, 전체를 다시 묶어 이음매를 본다.
- `craft.md`를 만들면서 계속 대조한다 (튕기는 착지는 이징 y1>1, 빛 효과는 둥근 모서리 안으로 자르기, 확대는 `zoom` 또는 2배 소재).
- 사용자가 "첫 번째 제목"처럼 대상이 애매하게 말하면 어느 것인지 먼저 확인하고 고친다.

```bash
# 프레임 → 영상 (소리 없이)
ffmpeg -y -framerate 30 -i work/frames/%05d.jpg -c:v libx264 -crf 18 -preset slow -pix_fmt yuv420p work/video.mp4
```

## 6. 소리 (통과 조건: 효과음표가 있고, 렌더 결과에서 효과음이 다 들림)

**화면 시간이 확정된 뒤에 한다.** 그 뒤 장면 길이 · 순서가 바뀌면 효과음표 전체를 다시 맞춘다.

- 음악: `--music` 파일이 있으면 그것, 없으면 로컬에서 합성한다 (ffmpeg `aevalsrc` · `sine`, 브라우저 `OfflineAudioContext`). 과금 생성 API 금지 (CLAUDE.md 원칙 12). 음악은 효과음 자리를 남기도록 낮게(약 0.34배) 깔고 처음 · 끝은 페이드.
- 효과음 성격: 화면 이동 = 휙, 착지 = 쿵, 쌓아 올림 = 상승음, 반짝임 = 빛, 전환 = 전환음. 게임 효과음 같은 합성 "뾰롱" 소리는 피한다. 다만 화면에 실제 동작(타이핑 · 클릭 · 스위치)이 있으면 그 동작의 소리를 낸다.
- 효과음표 `work/sfx.js`: `{ at, src, volume, 설명 }`. `at`은 숫자가 아니라 `SHOTS.x.start + 오프셋` 식으로 쓴다. 긴 소리는 동작 길이에 맞춰 자른다.
- 연속 효과음은 두 소리를 번갈아 쓰고, 음량을 계단식으로 낮추고(예: 0.40 → 0.25), 간격을 화면 곡선에 맞춰 좁힌다. 너무 촘촘해지면 휙 소리 하나로 녹인다.
- 끝맺음: 상승음(모이기 시작) → 쿵(로고 착지, 영상에서 가장 큰 소리) → 빛(여운).
- **싱크 보정**: AAC 인코딩은 소리를 앞에 덧대서(48kHz 에서 보통 약 1프레임) 늦게 들릴 수 있다. 렌더 뒤 날카로운 효과음 2~3개의 실제 위치를 재서, 어긋난 만큼 `at` 계산에서 한꺼번에 뺀다. 값과 잰 방법은 `plan.md`에 적는다. 다른 렌더 방식의 값을 가져다 쓰지 않는다.
- 같은 화면 · 같은 효과음에 음악만 뺀 판도 같은 시간표로 만든다 (별도 편집 금지).

## 7. 독립 검수 · 최종 렌더 (통과 조건: `review.md`의 반드시 고칠 항목 0)

1. 최신 판을 렌더하고 장면마다 최소 3프레임(등장 중 · 동작 절정 · 자리 잡은 뒤)을 뽑는다. 전체 흐름은 컨택트 시트로:
   ```bash
   ffmpeg -i promo.mp4 -vf "fps=1,scale=480:-1,tile=6x10" -frames:v 1 work/qa/contact.jpg
   ```
2. **검수 서브에이전트**(general-purpose)를 새로 부른다. 넘기는 것은 결과물과 기준뿐이다: 영상 두 판 경로, 뽑은 프레임 경로, `plan.md`, `references/review.md`, `references/craft.md`, 고른 기법 항목. 만들면서 한 변명 · 수정 이력 · "통과할 것" 같은 암시는 넘기지 않는다.
3. 결과를 `review.md`에. 고칠 항목은 성격에 따라 되돌아간다: 기획 · 장면표 문제 → 3단계, 화면 구현 → 5단계, 소리 → 6단계. 반드시 고칠 항목이 0이 될 때까지.
4. 장면마다 "이 장면이 새로 알려 주는 게 뭔가"를 묻고, 같은 정보 · 같은 문구가 두 번 나오면 지운다. 문구는 최종 화면을 보며 한 번 다시 쓴다.
5. 최종 렌더: 음악 판 · 음악 없는 판. 둘 다 H.264 · `yuv420p` · AAC · `+faststart`.
6. 포스터: 가장 강한 장면이 다 자리 잡은 순간을 장면표 시간으로 뽑아 `promo.jpg`, 두 판 모두 0번째 프레임에 굽는다 (프레임을 바꾸고 추가하지 않음).
   ```bash
   ffmpeg -ss 12.4 -i promo.mp4 -frames:v 1 -q:v 2 promo.jpg
   ffmpeg -y -i promo.mp4 -i promo.jpg \
     -filter_complex "[0:v][1:v]overlay=0:0:enable='eq(n,0)'[v]" \
     -map "[v]" -map "0:a?" -c:v libx264 -crf 18 -preset slow -pix_fmt yuv420p \
     -c:a copy -movflags +faststart promo.poster.mp4 && mv promo.poster.mp4 promo.mp4
   ```
7. `ffprobe`로 두 판의 길이 · 해상도 · fps · 프레임 수가 같은지 확인한다.
8. `share-copy.txt`: 1~3문장, 기능 이름과 구체적인 이득. `rules/frontend/copy.md` 해요체, 이모지 금지.

## 보고

- 두 판 · 포스터 · 문구 경로, `ffprobe` 결과
- 각도 한 문장, 기능-장면 배정 요약
- 검수 결과: 고친 항목 수, 남은 "권장" 항목, "확인 못 함" 항목
