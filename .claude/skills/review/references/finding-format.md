# finding 형식 · 심각도 (code-reviewer · security-reviewer · fe-ui-auditor 공용)

리뷰 · 감사 결과는 이 형식으로만 쓴다. 형식이 같아야 `/review` · `/audit`이 결과를 합쳐 분류할 수 있다.

## finding 한 건

```
- [심각도] 파일:줄
  문제: 무엇이 잘못됐는가 (한 문장)
  왜: 어떤 입력 · 상황에서 어떤 결과가 나는가 (보안이면 공격 시나리오 + 영향)
  수정: 구체적 방향
  확인: Given / When / Then 또는 수동 절차
```

- 파일:줄이 없는 finding은 쓰지 않는다. 위치를 못 잡으면 "열린 질문"으로.
- 근거를 코드에서 확인하지 못한 의심은 finding이 아니라 "판단 보류".

## 심각도

| 심각도 | code-reviewer | security-reviewer |
| ------ | ------------- | ----------------- |
| Critical | (안 씀) | 인증 우회, 비로그인 사용자의 데이터 접근 · 변경, 대량 노출 |
| High | 사용자에게 보이는 버그, 데이터 손상, 기존 기능 회귀, 보안 기본 위반 | 다른 사용자 데이터 접근 · 변경, admin 기능 접근, secret · 해시 노출 |
| Medium | 특정 조건에서 실패, 에러 · 상태 처리 누락, 계약 불일치 가능성 | 조건부 악용 입력 검증, 제한 없는 목록 · 업로드, 로그에 개인정보 |
| Low | 유지보수 위험, 나중에 버그가 될 구조 | 방어 심화, 설정 명확화 |

모든 항목을 High로 두지 않는다. 심각도는 **실제 영향** 기준이다. 요청 · 계획이 그 동작을 명시했더라도 결함이면 심각도를 낮추지 않고 "계획대로 만든 것" 라벨만 붙인다. 요청이 언급하지 않았다는 것은 허가가 아니다 — 사용자가 합리적으로 기대할 동작 기준으로 본다.

## 공통 섹션

리뷰 보고는 아래 순서. 빈 섹션도 "없음"이라고 쓴다.

1. **결과 한 줄**: 중대한 문제 없음 / Critical N · High N · Medium N · Low N
2. **Findings** (심각도순)
3. **판단 보류** — diff · 코드만으로 확정하지 못해 판단을 미룬 동작. 항목마다 무엇을 확인하면 결론이 나는지. **비어 있으면 "판단을 미룬 것 없음"이라고 명시** (조용한 누락을 막기 위한 칸)
4. **열린 질문** — 설계 · 운영 결정이 필요한 것
5. **남은 위험** — 문제는 아니지만 사용자가 알아야 할 것

## 하지 않는 것

- 칭찬, 취향 · 스타일 (실제 위험을 숨기는 경우만 예외)
- 호출자가 준 사전 판단("이건 문제 아님")을 그대로 받기 — 근거를 직접 확인한다
- 구현자의 "이렇게 한 이유" 설명을 근거로 심각도 낮추기 — 그건 자기 채점이다
- 비밀 값 출력 (위치와 사실만)
