현재 변경을 리뷰한다. 범위: $ARGUMENTS (비어 있으면 `git diff` + 새 파일 전체)

## 입력

- 범위 (`$ARGUMENTS`)
- 있으면: 변경 의도(요청 원문 · 수용 기준), 리뷰에서 뺄 것

## 절차

1. **리뷰 대상 확정**: `git status --short`, `git diff --stat`으로 변경 파일을 모은다. 변경 의도(어떤 요청으로 바뀐 것인지)를 한 줄로 적는다. 변경이 크면 위험 영역(인증 · 권한 · DB · 공개 API · 공통 컴포넌트)부터 본다.
2. **code-reviewer** 호출 → 버그 · 회귀 · 검증 공백 · 유지보수 위험을 심각도순 findings로 받는다. 변경 의도와 리뷰 제외 목록을 함께 넘긴다. **리뷰어에게 결론을 미리 주지 않는다** — "이건 문제 아님", "심각도는 낮게" 같은 사전 판단 금지. 제외 목록은 영역(스타일 · 범위 밖)만.
3. 변경에 **인증 · 권한 · 쿠키 · 입력 처리 · 외부 호출 · 파일 업로드**가 포함되면 **security-reviewer**도 호출한다. 둘은 독립적이므로 함께 돌려도 된다. 심각도 · finding 형식은 `references/finding-format.md`를 두 에이전트가 공유한다.
4. **findings 분류** — 리뷰 결과는 그대로 수정 목록이 아니다:

   | 분류 | 처리 |
   | ---- | ---- |
   | 실제 버그 | 수정 제안 + 재발 방지 확인 방법 |
   | 불확실한 위험 | 코드 근거 · 재현 조건을 더 확인해야 할 것 |
   | 검증 공백 | 수용 기준 · 상태 처리 · 에러 처리에서 빠진 케이스 (Given / When / Then) |
   | 설계 질문 | 사용자 결정으로 넘길 것 |
   | 범위 밖 | `zz_docs/TODO.md`에 적을 것 |

5. 보고한다. 단독 호출이면 **고치지 않는다**. 고칠지, 무엇부터 고칠지는 사용자가 정한다. 다른 스킬의 마무리 단계에서 불렸으면 "실제 버그"만 그 스킬에서 고치고 다시 `/verify`.
6. 리뷰어의 **"판단 보류" 목록**(diff만으로 확인 못 한 것)은 호출자가 직접 코드를 열어 해소하고 결과를 보고에 적는다. 비워 두지 않는다.

## 리뷰 결과를 반영할 때

- finding에 동의하든 반박하든 **근거로만** 말한다. "맞습니다", "좋은 지적입니다" 같은 문구를 쓰지 않는다.
- finding 중 하나라도 이해되지 않으면 **아무것도 고치지 않고** 먼저 확인한다.
- 리뷰어가 틀렸다고 판단하면 파일:줄 근거를 들어 그렇게 적는다. 리뷰어의 말이라고 무조건 반영하지 않는다.
- 반영은 한 finding씩, 각각 `/verify`로 확인한다.

## 돌려줄 형식

```
## 리뷰 결과: 중대한 문제 없음 / 수정 필요 N건

변경 의도: ...
리뷰 범위 / 제외: ...

### Findings (심각도순, 한 건 형식은 references/finding-format.md 그대로)
- [High] 파일:줄
  문제 / 왜 / 수정 / 확인
- [Medium] ...

### 보안 (security-reviewer를 돌렸을 때, 같은 형식 + Critical)

### 검증 공백
- Given / When / Then ...

### 판단 보류 (리뷰어가 미룬 것을 호출자가 해소한 결과. 없으면 "없음")
### 열린 질문
### 범위 밖 · 남은 위험
```

문제가 없으면 "중대한 문제 없음"이라고 분명히 말하고, 남은 위험을 따로 적는다.

## 하지 않는 것

- 파일 수정
- 칭찬, 취향 · 스타일 지적 (실제 위험을 숨기는 경우만 예외)
- 파일 · 줄 근거 없는 일반론
- 심각도 없이 나열
- 이미 `zz_docs/TODO.md`에 있는 문제를 새 finding으로 올리기
