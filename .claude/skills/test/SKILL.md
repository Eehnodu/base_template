$ARGUMENTS 의 테스트 케이스를 설계한다. **테스트는 많이 돌리는 것이 아니라, 이 변경을 검증하는 가장 작은 케이스를 정확히 고르는 것이다.**

> 현재 상태: base에 테스트 러너가 없다. 이 스킬은 케이스 설계 · 수동 확인 절차까지 만든다. pytest · vitest 도입은 `zz_docs/TODO.md` 2단계 항목이며, 도입되면 4단계를 실제 테스트 작성으로 바꾼다.

## 입력

- 필수: 대상 (`$ARGUMENTS`)
- 있으면 좋은 것: 수용 기준, 변경 유형(단일 함수 · UI · API · DB · 인증)

## 1. 기존 테스트 구조 확인

`frontend/`와 `backend/`에서 테스트 프레임워크 · 테스트 파일 · 실행 명령을 찾는다. 없으면 **없다고 보고**하고 진행한다 (추정으로 명령을 만들지 않는다).

## 2. 변경 유형별 검증 수준

| 변경 유형 | 먼저 확인할 것 | 추가 확인 |
| --------- | -------------- | --------- |
| 단일 함수 · 유틸 | 정상 · 경계 · 빈 입력 | 호출하는 곳의 결과 |
| UI 컴포넌트 · 화면 | 네 가지 상태(로딩 · 데이터 · 빈 · 에러), 360/768/1280 | 키보드 조작, 다크모드 |
| API | 정상 응답 필드, 400 · 403 · 404 · 409 각 에러 코드 | 로그인 없이 호출 → 401, 다른 사용자 id → 403 |
| DB 모델 | 마이그레이션 적용 · 롤백, 기존 데이터 | NOT NULL · unique 제약과 기존 행 |
| 인증 · 권한 | 실패 경로 전부 (만료 · 위조 · 타입 불일치) | admin ↔ user 경계 |

## 3. 케이스 설계

정상 경로 · 경계 조건 · 실패 조건 · 권한 조건을 각각 하나 이상 포함해 Given / When / Then으로 쓴다.

```
- Given [상황] / When [행동] / Then [결과] — 커버하는 위험:
```

구현 세부사항이 아니라 **사용자에게 보이는 동작**을 검증하는 케이스로 쓴다.

케이스마다 먼저 답한다: **"어떤 프로덕션 코드 변경이 이 케이스를 실패시키는가?"** 답이 없으면 그 케이스는 아무것도 지키지 못한다. 피할 것:

- 코드가 계산한 값을 그대로 기대값으로 쓰는 케이스 (항상 통과)
- 상수 · 문구 · 특정 줄의 존재를 확인하는 케이스 (동작이 아니라 변경 여부만 감지)
- 목(mock)이 너무 많아 실제 코드가 거의 실행되지 않는 케이스

## 4. 실행 방법 (현재)

러너가 없으므로 케이스마다 **수동 확인 절차**를 붙인다.

- 백엔드: 호출 방법(`curl` 또는 브라우저 개발자 도구)과 기대 응답 · errorCode. 로컬 서버는 `./run.sh`.
- 프론트: 화면 · 폭 · 조작 순서 · 기대 결과.
- 정적 검사(`/verify`)는 항상 먼저.

러너가 도입되면: 기존 테스트 스타일을 따라 케이스를 코드로 옮기고, 실패 시 **제품 버그인지 테스트 버그인지** 구분해 보고한다. 테스트를 삭제 · skip해서 통과시키지 않는다.

## 5. 보고

- 케이스 목록(Given / When / Then + 커버하는 위험), 케이스별 확인 절차, 자동화할 수 없는 것과 이유, 기존 테스트 구조 유무.

## 하지 않는 것

- 존재하지 않는 테스트 명령 추정
- 정상 케이스만 설계
- 구현 내부 구조에 묶인 케이스
- 러너 없이 "테스트 통과"라고 보고
