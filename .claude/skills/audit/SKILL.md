$ARGUMENTS 화면을 감사한다. **파일을 고치지 않는다.** 결과는 코드로 확정한 finding과, 사용자가 브라우저에서 볼 확인 목록 두 가지다.

## 입력

- 범위 (`$ARGUMENTS`). 비어 있으면 `git diff --stat`에서 바뀐 `frontend/src/container/**` · `component/**` 화면
- 단계: 개발 중(기본) / 마무리 — 마무리면 심각도가 한 단계 올라간다

## 절차

1. **범위 확정**: 화면(container)이면 그 화면이 쓰는 컴포넌트까지 포함한다 (import 따라가기). admin/client 구분을 적는다. 화면 5개를 넘으면 나눠서 돈다.
2. **fe-ui-auditor** 호출 → 범위 · 단계 · admin/client를 넘긴다. 토큰 정의 파일을 같이 읽으라는 것은 에이전트 규칙에 있다.
3. **분류**:

   | 분류 | 처리 |
   | ---- | ---- |
   | High (접근성 위반 · 상태 누락 · 자리 표시 데이터) | 수정 권고 — `/design` 또는 `/fix`로 |
   | Medium | 목록으로 보고, 고칠지는 사용자 |
   | Low | `zz_docs/TODO.md`에 적을지 물음 |
   | 브라우저 확인 목록 | 사용자에게 화면 · 폭 · 조작으로 전달 |
   | 판단 보류 | 호출자가 코드를 열어 해소, 못 하면 확인 목록으로 |

4. **보고**. 단독 호출이면 고치지 않는다. `/design` · `/fullstack` 마무리에서 불렸으면 High만 그 스킬에서 고치고 `/verify frontend`.

## 돌려줄 형식

fe-ui-auditor 형식 그대로 + 맨 위에 한 줄 결론: "수정 필요 N건(High N) · 브라우저 확인 N건" 또는 "코드상 문제 없음 · 브라우저 확인 N건".

## /review · /verify 와의 차이

- `/verify`: 명령(타입 · lint · 빌드) + 바뀐 파일의 grep 규칙. 기계적.
- `/review`: `git diff` 기준 로직 · 회귀 · 보안.
- `/audit`: **화면 단위 전체**(바뀌지 않은 파일 포함)의 UI 품질. 접근성 · 상태 · 폼 · 반응형 · 모션 · 위계 · 문구.

## 하지 않는 것

- 파일 수정
- 점수 · 등급 매기기
- 렌더링해야 알 수 있는 것을 확정 finding으로 쓰기
- 범위 밖 화면까지 넓히기 (본 것은 "범위 밖에서 본 것"에만)
