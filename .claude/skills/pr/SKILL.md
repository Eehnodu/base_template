현재 변경을 커밋 · PR로 정리한다. $ARGUMENTS 가 있으면 PR 제목 후보로 쓴다.

## 1. 변경 점검

- `git status --short`, `git diff --stat`, `git log --oneline -10`, 현재 브랜치
- 변경 파일을 목적별로 묶는다. **요청 범위를 벗어난 변경**, 설정 · lock 파일 변경, 삭제 파일을 따로 표시한다.
- `zz_docs/TODO.md` "마지막 검증"과 대조해 **현재 변경에 대한 검증이 있었는지** 확인한다. 없거나 검증 뒤에 코드가 바뀌었으면 먼저 `/verify`를 제안한다.
- diff에 비밀정보(토큰 · 키 · 비밀번호 · `.env` 내용)가 없는지 확인한다.
- base는 1인 개발이라 `main`에 직접 커밋한다. 브랜치 전략이 생기면 그것을 따른다.

## 2. 커밋 분리 · 메시지

- 한 커밋에 한 주제. 기능 · 문서 · 포맷 · 의존성 변경이 섞여 있으면 분리안을 제안한다.
- 메시지는 `type(scope): 요약` (feat · fix · docs · refactor · chore) + 필요하면 본문(왜 바꿨는지, 하지 않은 일). **diff에 없는 내용은 쓰지 않는다.** 후보 2~3개와 고른 이유를 보여 준다. 문체는 `rules/writing.md` — 본문 · PR 본문에 "단순히 X가 아니라 Y", 마무리 한 줄, 과장어("강력한" · "원활하게"), 챗봇 잔재를 넣지 않는다.
- 커밋은 바로 실행한다 (사용자 지시, `settings.json` allow). 사용자가 만든 변경이 섞여 있으면 그것만 먼저 묻는다.

## 3. PR 본문 초안

```
## Summary
- 변경 요약

## Why
- 문제 · 요구사항

## Changes
- 구체적 변경 (백엔드 / 프론트 / 문서)

## Tests
- [x] 실행한 검증 (명령 · 결과)
- [ ] 실행하지 못한 검증과 이유
- 수용 기준 충족 여부

## Risks
- 위험과 완화 방법. 마이그레이션 · 환경변수 · 계약 변경이 있으면 여기에

## Review Focus
- 리뷰어가 특히 볼 파일:줄과 이유
```

- 실행하지 않은 검증은 **실행하지 않았다고** 적는다. 과장 표현을 쓰지 않는다.
- UI 변경이 있으면 스크린샷 자리를 남기고 사용자에게 요청한다.
- 아직 끝나지 않은 작업이면 draft PR로 제안하고 "병합 전 남은 조건"을 적는다.

## 4. 생성 (승인 후)

- 푸시는 커밋 뒤 바로. PR 생성(`gh pr create`)만 승인 후에. 원격이나 `gh`가 없으면 본문만 넘긴다.
- 생성 후 URL을 보고한다.

## 하지 않는 것

- 승인 없는 PR 생성
- 테스트하지 않았는데 테스트한 것처럼 쓰기
- 여러 주제를 한 커밋 · 한 PR에 섞기
- 사용자가 만든 변경을 모르고 함께 커밋 (의심되는 파일은 먼저 묻는다)
- git 명령에 `cd` · 파이프(`| tail` 등)를 섞기 (허용 목록 밖 조각이 있으면 승인창이 뜬다)
