# 글쓰기 기준 — AI 냄새 빼기

문서(README · `zz_docs/` · CHANGELOG · 온보딩), 커밋 메시지 · PR 본문, 사용자에게 주는 보고에 적용한다. 코드 주석 · docstring · 화면 문구는 각 규칙 문서를 따른다.

원칙은 하나다. **남기는 문장마다 독자가 아직 모르는 것을 하나씩 더한다.** 모델은 가장 넓은 독자에게 무난한 선택을 반복하고, 사람은 한 독자 · 한 주제를 위해 고르지 않게 쓴다. 아래 패턴은 전부 "무난한 기본값"의 흔적이다. 사실을 지어내지 않는다 — 문장을 고치다가 근거 없는 이름 · 숫자 · 날짜 · 주장을 넣지 않는다 (`doc-writer` 근거 수준 표).

## 1. 강조하는 척하기 — 한 번 보이면 고친다

| 패턴 | 예 | 고치는 법 |
| ---- | -- | --------- |
| 아닌 것부터 말하기 | "단순히 X가 아니라 Y다", "X가 아닌 Y", "이건 X의 문제가 아니다. Y의 문제다" | 아무도 X라고 하지 않았다. Y만 말한다. 독자가 실제로 X라고 믿을 때만 대비를 남긴다 |
| 마무리 한 줄 | 앞 문단을 되풀이하는 한 문장 단락, "이게 핵심이다", "그 차이가 중요하다", 절마다 같은 맺음말 | 새 사실 · 결과를 더하지 않으면 지운다 |
| 깊어 보이는 말 | "본질적으로", "결국 중요한 건", "X는 Y의 언어다", "X가 되면 함정이다" | 구체적인 주장으로 바꾼다 |
| 뜸 들이는 도입 | "자, 살펴보자", "알아야 할 것은 이렇다", "솔직히 말하면", "핵심은 이거다" | 도입을 지우고 바로 말한다 |
| 없는 반론과 싸우기 | "X를 말하려는 게 아니다", "혹자는 ~라고 하지만", "쉬운 방법은 ~이겠지만" | 초안 흔적이다. 반론이 실제로 있을 때만 남기고, 아니면 주장만 쓴다 |

## 2. 리듬을 규칙으로 만들기

- **3개씩 나열.** 뜻이 셋이 아닌데 셋으로 맞추지 않는다 ("혁신, 영감, 통찰"). 항목마다 다른 뜻이 있는지 본다. 없으면 합치거나 하나를 키운다.
- **대시(—)로 문장 잇기.** 문장 안에서 두 절을 "—"로 잇지 않는다. 마침표 · 쉼표 · 괄호로 관계를 고른다. **base 관례로 허용하는 곳**: 제목 · 표 셀 · 커밋 제목의 부제 구분("fix(ui): 글자색 수정 — 다크모드 대비"), 항목 나열의 " · ", 그리고 `.claude/` 규칙 · 스킬 문서의 "규칙 — 이유" 구분(Claude가 읽는 지시문이라 짧은 부연 구분자로 쓴다). 코드 · 경로 · 명령 안의 대시는 손대지 않는다.
- **같은 주어로 시작하는 문장 연속.** 합치거나 주어를 바꾼다.
- **한정어 쌓기.** "경우에 따라 어느 정도 가능할 수도" 처럼 이전 과장을 무마하려 붙인 한정어를 걷어낸다. 근거가 있는 불확실성 · 범위 · 안전 경고는 남긴다.

## 3. 부풀리기

- **과장어.** "핵심적인", "강력한", "혁신적인", "원활하게", "손쉽게", "획기적인", "다양한", "풍부한", "심층", "전략적" — 사실을 두고 꾸밈을 뺀다. 기술 용어로 쓰는 "robust"(견고성) 같은 건 남긴다.
- **의미 부여.** "~의 중요한 전환점", "~의 초석을 놓았다", "앞으로가 기대된다" — 사실만 남기고 마지막 구체적 사실로 끝낸다. "향후 계획" 절은 실제 계획이 있을 때만.
- **모호한 연결.** "~와 관련된", "~와 연계된" — 어떤 관계인지 안다면 그 관계를 쓴다. 모르면 지어내지 않고 모호한 표현을 그대로 둔다.
- **빌려온 권위.** "전문가들은", "업계에서는", "여러 자료에 따르면" — 실제 출처가 있으면 그것을, 없으면 주장을 뺀다.
- **~하며 · ~함으로써 꼬리.** "…을 강조하며", "…을 보장함으로써" — 단순한 사실 뒤에 붙은 의미 부여. 근거가 있을 때만 남긴다.
- **"이다 · 있다"를 피하는 버릇.** "~로 기능한다", "~를 자랑한다", "~를 제공한다" 대신 "이다 · 있다".

## 4. 서식을 규칙으로 만들기

- **장식용 볼드.** 이유 없는 볼드, 목록 항목마다 `**라벨:**`을 붙이는 습관. 라벨이 정보(필드명 · 키)면 남기고, 장식이면 뺀다. 라벨 없이 문장이 통하면 문장으로 푼다.
- **이모지 전면 금지.** 제목 · 목록 · 본문 · 표 셀 · 커밋 · PR · 답장 어디에도 쓰지 않는다. 상태 표시도 글자로 한다: "적용 · 보류 · 안 씀", 체크리스트는 `[x]`. 예외 없음 (사용자 지시, 2026-09-28).
- **장식용 제목.** 제목에 화살표(→) · 구분 기호, 절마다 구분선, 문서 제목을 첫 문장에서 반복. 제목은 그 절에 무엇이 있는지 말한다 ("결정, 한 화면에"가 아니라 "선택지 6개 비교").
- **제목 바로 밑 한 줄 요약.** "## 성능" 밑에 "속도는 중요하다." — 지운다.

## 5. 대화 · 초안의 찌꺼기 — 보이면 지운다

- **챗봇 잔재.** "도움이 되셨길 바랍니다", "물론입니다!", "좋은 질문입니다", "궁금한 점 있으면 말씀해 주세요", "계속할까요?" — 문서 · 커밋 · PR에 남지 않게 한다.
- **모른다고 하고 추측하기.** "공개된 자료는 없지만 아마 ~였을 것이다" — 근거가 없으면 "확인 필요"로 표시하거나 문장을 뺀다 (`doc-writer` 규칙 3).
- **문서가 자기 얘기하기.** "이 함수는 이전 방식을 대체하기 위해 추가됐다", "아래 표는 ~를 비교한다", "확인 안 된 건 추측하지 않고 표시했다" — 대상을 말한다. 이전 버전 얘기는 CHANGELOG · 마이그레이션 문서에서만. 독자가 눈으로 보는 배치 · 순서 설명은 뺀다.

## 6. 독자를 잘못 잡기 — 답장 · 보고

같은 대화 안의 답장, PR 리뷰 답글, 작업 보고는 독자가 배경을 이미 안다.

- **결정을 먼저** 쓴다. 문제 재진술 → 진단 → 증거 → 결론 순서로 쌓다가 답이 마지막 줄에 오지 않게 한다.
- 근거는 **독자의 동의를 바꿀 사실 하나**와 행동에 필요한 링크만. 진단 과정과 "이 계획이 될 거라는 증명"은 티켓 · 문서로 보낸다.
- 상대가 쓴 배경, 이미 합의한 것을 되풀이하지 않는다.

## 7. 고칠 때 순서 (`/docs` 에서 문체를 다듬을 때)

1. **표시.** 전체를 한 번 읽고 패턴을 센다. 문단 모양도 본다 (절마다 같은 맺음말, 예시 세 개 나열).
2. **초안.** 뜻 · 근거 있는 주장은 전부 유지. 길이 · 구조는 바꿔도 된다. 사실은 추가하지 않는다.
3. **점검.** 소리 내 읽듯 다시 본다. 사실 · 숫자 · 이름 · 주장이 빠지거나 생겼는지 확인한다. 1절 대비 · 마무리 한 줄 · 3개 나열 · 대시 · 장식 볼드는 고친 뒤에도 잘 남는다.
4. **최종.** 표시된 구절을 하나씩 땜질하지 말고 문단의 요점을 다시 쓴다. 문장 길이를 섞는다.

## 8. 손대지 않는 것

- 사용자가 문체 샘플을 주면 **샘플이 위 규칙보다 우선**한다 (대시 빈도까지).
- 인용문 · 제목 · 고유명사 · 그 표현 자체를 설명하는 문장 안의 표현.
- 편지 · 댓글의 인사와 맺음말.
- 글쓴이의 목소리: 구체적이고 별난 세부, 정리되지 않은 양가감정, 설명할 수 있는 1인칭 선택, 진짜 여담 · 자기 정정.
- 패턴 하나는 사람도 일부러 쓴다. 1 · 5절은 한 번 보여도 고치고, 나머지는 같은 문단에 다른 패턴이 함께 있을 때 고친다.
