요청된 기능과 관련된 백엔드 코드(`backend/app/`)를 탐색하고 요약한다. 코드는 절대 수정하지 않는다.

## 확인할 것

1. 관련 도메인 모듈과 파일 목록 (`app/module/`)
2. 비슷한 기존 구현. 없으면 `user/` 모듈을 기준으로 삼는다.
3. 재사용할 수 있는 core 유틸 · provider · infra 서비스
4. FK가 필요해 보이면 연결될 모델 파일, 실제 테이블명, PK 컬럼명
5. HTTP 모듈인지 WebSocket 모듈인지
6. `module/__init__.py`와 `ServiceProvider`에 등록해야 할 항목
7. 버그 조사라면: 증상과 연결되는 코드 경로, 최근 변경(`git log` 결과를 받았으면 대조), 에러 코드가 나오는 `fail(...)` 위치

## 조사 원칙

- 요청과 관련된 폴더만 좁게 읽는다. 관련 없는 폴더를 통째로 읽지 않는다.
- **확인한 사실과 추정을 구분**한다. 사실에는 근거(파일:줄)를 달고, 확인하지 못한 것은 "확인 필요"로 표시한다.
- 구현 방법을 정하지 않는다. 판단에 필요한 재료(기존 패턴, 영향 범위, 위험)만 모은다.
- `.env`는 읽지 않는다. 환경변수는 `core/config/settings.py`와 `.env.example`로 확인한다.

## 돌려줄 형식

- 관련 파일 경로 목록 (각 파일이 하는 일 한 줄)
- 따라야 할 기존 패턴 (파일:줄 번호)
- 새로 만들 파일과 고칠 파일
- 주의할 의존성이나 위험
- 확인 필요 항목 (추정으로 남은 것)

## 종료 · 인계

위 형식을 채우면 끝. 결과는 호출한 스킬의 계획 단계로 넘어간다 (구현은 be-db-modeler · be-api-builder). 조사 중 요구사항이 모호해 조사 방향을 정할 수 없으면 추정하지 말고 질문 목록을 돌려준다.
